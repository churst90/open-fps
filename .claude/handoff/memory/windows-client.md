2026-09-29: Cody's friend plays the **Windows client** (NVDA) against a server on Cody's **VPS**
(UDP 33288 already forwarded). Read `docs/WINDOWS_AND_SERVER.md` first.

- `./publish-windows.sh` -> `dist/OpenFPS-windows-<build>.zip` (Release, self-contained, ~430 MB).
  `./publish-server.sh [rid]` -> `dist/openfps-server-<rid>-<build>.tar.gz`, no accounts db in it.
  Both build under `~/.cache/openfps-publish`, never /tmp ([[tmp-is-eight-gigabytes-of-ram]]).
- `<build>` is `WireContract.Hash`: sha of OpenFPS.Common's own .cs files, generated by an inline
  MSBuild task in OpenFPS.Common.csproj. `LoginRequest.Build` carries it; the server refuses a UDP
  login that differs. Any change to Common means a new zip for the friend AND a server update.
  The GTK client sends it too, so a stale GTK client is refused ([[restart-the-server-always]]).
- `OPENFPS_ADMIN_PASSWORD` seeds/resets the admin password; a public server must set it once.
- Windows head = `OpenFPS.Client/` (WinForms). Keys from the game window (no global hook), Alt-alone
  menu swallowed, NVDA checked per line with SAPI fallback, menus speak only when NVDA is NOT
  running (NVDA announces native controls itself). Has "Create account" and NAudio voice chat,
  which GTK lacks.
- Never run on Windows from here (no Wine). The friend's logs are the only instrument: main menu
  "Open log folder".

**Why:** the Windows head had not been touched since 09-13 and had drifted (no machines/*.json, no
settings, a global key hook). **How to apply:** when the GTK head gains a feature, say whether the
Windows head needs it too; `ClientRunner.cs` mirrors GTK `Program.cs`.
