# Audio engine test coverage, 2026-09-24

Line coverage from the full test suite (`coverlet.collector`, `--collect:"XPlat Code Coverage"`) at
commit `c72cf93`. 927 tests; 3 real-time-budget tests failed only because the collector slows
everything down (they pass in a normal run). Generated MemoryPack serialisers are left out.

How to repeat it:

    DOTNET_CLI_USE_MSBUILD_SERVER=0 ~/.dotnet/dotnet test OpenFPS.Tests --artifacts-path /tmp/openfps-cov \
        -nodeReuse:false -p:UseSharedCompilation=false --collect:"XPlat Code Coverage" \
        --results-directory /tmp/openfps-cov/results

It takes about 1 h 30 min with the collector (18 min without).

## Uncovered and weakly covered code

### 1. ClientAudioSystem (9%): what gets played

None of these run in any test:

- `Update` (217 lines), `ProcessAudioEmitter` (205)
- `ChooseLiveEngines` (153), `ChooseLiveMachines` (52), `ChooseFrontVoices` (34): which vehicles
  get a live voice
- `LookUpPhysicalLevel` (33): the level a physical voice is placed at
- `UpdateHorns` (56), `UpdateSirens` (25), `SirenVoice` (49)
- `DistantEngine` (41), `FrontVoice` (36)
- `TyreDemand` (26), `SubmitFootstep` (27), `SubmitLanding` (24), `SubmitStepReflections` (37)

Several past faults lived here (the level a voice was placed at, which voice won a slot). The fake
`IAudioProvider` in `VoiceLifecycleTests` can drive most of it without FMOD.

### 2. FmodAudioProvider (2%) and the DSP callbacks

`FmodAudioProvider.cs` is 2,174 uncovered lines across 58 methods. It needs a real FMOD system,
which the tests do not start. The DSP read callbacks are all at 0%: `EngineProcessor`,
`TapProcessor`, `EchoProcessor`, `MachineProcessor`, `SynthProcessor`, `GranularProcessor`,
`BoundaryProximityProcessor`, plus `GranularBank`, `MasterTap` and the `EngineRenderPool`
constructor. The voice states behind them are tested; the glue that copies their samples to FMOD
is not. Four of the past crashes were in this glue (see memory: mixer callbacks must not throw).

### 3. Acoustics (24%)

- `AsyncAcousticWorker`: `RunSteamAudio` (85), `BuildSimPath` (63), `AddEarlyReflections` (43),
  `RunListenerReverb`, `EvictStaleSources`, `RebuildSceneIfNeeded`, `BarrierPathDifference` all 0%;
  `WorkerLoop` 49%, `HandRolledPath` 22%.
- `EngineReflections` (6%): `Update`, `Make`, `SyncGeometry`, `Blocked` all 0%.
- `VehicleShadow.Apply` 0% (the Maekawa maths around it is tested, the application to a voice is not).
- `AcousticPathfinder.FindPath` 3%.
- `SpatialAcoustics.CalculateAcousticPaths` 39%.

### 4. Steam Audio (6%)

`SteamAudioSimulator`, `SteamAudioScene.Build`, `SteamAudioDsp`, `AmbisonicBedDsp` are untested:
they need the native Phonon library. `SteamAudioLiveTest` (252 lines, 0%) is a manual diagnostic,
not a test.

### 5. Smaller gaps in the synthesis

- Rail: `SteamFrontEnd.Step` 0% (steam locomotives are not on any map), `BogieVoice.Strike` 0%,
  `BogieVoice.Step` 49%, `TrainSynth.UpdateSlow` 0%.
- `WeaponSynth.CompositeBlast` and `ReadWav16Mono` 0%. The gunfire work replaces this path.
- `AudioPhysics.AtmosphericBands` 0%.
- `Loudness.cs` 80%, `Honk.cs` 76%.
- `GeometryUtils.cs` 55%: `RayIntersectsCone`, both `RayIntersectsCylinder`, `LineIntersectsCylinder`
  and `AABBIntersectsOBB` are 0%. The acoustics only use boxes today, so these are only reached by
  non-box colliders.

## Suggested order

1. `ClientAudioSystem` voice selection and level placement, through the fake provider: the
   highest-value untested code, and where level faults have come from before.
2. `VehicleShadow.Apply` and `EngineReflections`: small, pure enough to test, and both built
   recently without being heard.
3. The DSP callbacks: one test per processor that runs its callback on a buffer and checks the
   output is finite and matches the voice state it reads.
4. `AsyncAcousticWorker` paths that do not need Steam Audio (`HandRolledPath`,
   `BarrierPathDifference`, `EvictStaleSources`).
